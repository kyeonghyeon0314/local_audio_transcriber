# Local Multimodal Transcriber

녹음 파일과 발표자료 PDF를 넣고 실행하면, 로컬 PC의 **Gemma 4 E4B IT**가 **원본 오디오와 PDF를 직접 참고해** 화자를 구분한 전사 TXT를 만들어 줍니다.
Gemini에 녹음과 PDF를 올려 전사하던 작업을 클라우드 없이 PC에서 처리하는 것이 목표입니다.

- Whisper 같은 별도 STT를 쓰지 않습니다. 잘라낸 **원본 파형을 그대로** 멀티모달 모델에 넣습니다.
- PDF는 요약하지 않고, 기술용어·약어·고유명사를 바로잡는 **근거 자료**로만 씁니다.
- 한국어와 영어가 섞인 발화를 번역하지 않고 **말한 그대로** 남깁니다.

```
[00:03:21] Speaker 1:
여기서는 MPCC를 사용했습니다.
[00:03:28] Speaker 2:
그러면 lateral acceleration 제한은 얼마인가요?
[웃음]
```

## 요구 사항

- Windows 10/11
- NVIDIA GPU, VRAM 8GB 이상 권장 (RTX 5060 8GB 기준으로 설정됨). GPU가 없으면 CPU로 동작하지만 매우 느립니다.
- Python 3.10 이상 (3.14에서 확인, [python.org](https://www.python.org/downloads/)에서 설치할 때 "Add python.exe to PATH" 체크)
- Hugging Face 계정 (Gemma 라이선스 동의용)
- 디스크 여유 공간 30GB 이상 권장 (PyTorch와 모델 파일)

## 설치 (최초 1회)

1. 이 저장소를 내려받습니다 (Code → Download ZIP 후 압축 해제, 또는 `git clone`).
2. [google/gemma-4-E4B-it](https://huggingface.co/google/gemma-4-E4B-it) 페이지에서 라이선스에 동의합니다.
3. **`setup.bat`** 을 더블클릭합니다.
   - 가상환경(`.venv`), PyTorch(CUDA 12.8), 필요한 패키지를 설치합니다.
   - 마지막에 Hugging Face 토큰을 묻습니다. [토큰 페이지](https://huggingface.co/settings/tokens)에서 Read 토큰을 만들어 붙여 넣으세요.

## 사용법

**방법 1: input 폴더**

1. `input` 폴더에 녹음 파일(wav, mp3, m4a 등)과 발표자료 PDF를 넣습니다.
2. **`run.bat`** 을 더블클릭합니다.
3. 끝나면 `output` 폴더가 열리고 `녹음파일명_transcript.txt`가 생성되어 있습니다.

**방법 2: 끌어다 놓기**

녹음 파일과 PDF를 함께 선택해 `run.bat` 아이콘 위에 끌어다 놓습니다.

참고:
- 처음 실행할 때는 모델 파일(십수 GB)을 내려받으므로 오래 걸립니다.
- 녹음 여러 개를 한 번에 넣어도 됩니다. 녹음과 **파일명이 같은 PDF**가 있으면 그 PDF를, 없으면 넣은 PDF 전체를 참고합니다.
- PDF 없이 녹음만 넣어도 동작합니다.
- 처리 중에는 구간마다 결과 파일을 갱신합니다. 중간에 창을 닫아도 그때까지의 결과는 남습니다.
- 같은 이름의 결과가 이미 있으면 덮어쓰지 않고 `_transcript_2.txt`처럼 새 이름으로 저장합니다.

## 동작 방식

```
recording.m4a ─→ 16kHz mono 변환 ─→ 화자 구분 보조 모델 (CPU, 텍스트 변환 없음)
                                        "0.4~1.7초 화자1, 5.9~13.6초 화자2, ..."
                                                     │
                     같은 화자 연속 구간 → 턴, 턴들을 오디오 합 25초 이하로 묶음
presentation.pdf ─→ 페이지 텍스트 추출               │
                                  ↓                  ↓
      [고정 프롬프트 + PDF 문맥 + "[1] Speaker 2:" 원본 오디오 + "[2] Speaker 1:" 원본 오디오 ...]
                                  ↓
                         Gemma 4 E4B IT (로컬)
                                  ↓
                  "[1] ...", "[2] ..." → recording_transcript.txt
```

### 화자 구분

- Gemma 4는 E4B와 12B 모두 **목소리를 구분하지 못했습니다**(아래 실측 참고). 그래서 화자 구분만 작은 보조 모델에 맡깁니다. 계획서 9절의 "speaker embedding 기반 diarization 보조 기능"입니다.
  - 발화 구간 검출: pyannote segmentation-3.0 / 화자 임베딩: WeSpeaker ResNet34 ([sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), ONNX)
  - 첫 실행 때 `models/` 폴더로 자동으로 내려받습니다(약 33MB). CPU에서만 동작해 VRAM을 쓰지 않습니다.
- 보조 모델은 **"누가 언제 말했는지"만** 판단합니다. 텍스트는 여전히 Gemma가 그 화자 턴의 **원본 오디오를 직접 듣고** 만듭니다.
- 여러 턴을 번호 붙인 오디오 여러 개로 **한 번에** 넣습니다. 턴마다 따로 호출하면 "네" 같은 짧은 턴에서 앞 문맥을 베껴 쓰는 문제가 있었습니다.
- 화자 번호는 녹음에서 처음 말한 순서대로 붙습니다. 화자가 실제보다 많이 나오면 `diarization.threshold`를 올리고(예: 0.8), 적게 나오면 낮추세요. 화자 수를 알면 `num_speakers`에 적으면 됩니다.
- `diarization.enabled: false`로 두면 예전 방식(25초 구간, 5초 겹침, Gemma만 사용)으로 동작합니다. 이때는 화자 구분이 거의 되지 않습니다.

### 공통

- Gemma 4는 오디오를 한 번에 최대 30초까지 받기 때문에 긴 녹음은 자동으로 나눕니다.
- 지시문과 PDF 문맥은 모두 **오디오보다 앞에** 둡니다. 오디오 뒤에 둔 지시는 무시되고 "네, 알겠습니다." 같은 대답이 나왔습니다(`diagnose.bat`의 A/B 비교).
- (구간 방식) 각 구간에는 직전 전사의 끝부분과 지금까지 나온 화자 번호를 함께 넘겨 **Speaker 번호가 구간마다 바뀌지 않도록** 합니다.
- (구간 방식) 모델은 겹치는 5초를 포함해 구간 전체를 전사하고, 프로그램이 이전 전사의 끝과 새 전사의 앞을 **글자 단위로 정렬해 겹친 부분을 잘라냅니다**. 모델에게 겹친 부분을 건너뛰라고 하면 들쭉날쭉하게 따라서 이 방식을 씁니다.
- 모델이 같은 말을 끝없이 반복하면(예: "그... 그... 그...") 한 번으로 줄입니다.
- 각 구간의 모델 원본 출력은 `output/logs/*_chunks.log`에 저장됩니다. 품질을 비교하거나 프롬프트를 조정할 때 참고하세요.

## 설정

- **`prompt.txt`**: 모델에 매번 주는 고정 지시문입니다. 코드를 고치지 않고 이 파일만 수정해도 됩니다.
- **`config.yaml`**: 기본값 그대로 쓰면 됩니다. 자주 바꿀 만한 항목은 다음과 같습니다.

| 항목 | 기본값 | 설명 |
|---|---|---|
| `model` | `google/gemma-4-E4B-it` | Hugging Face 모델 ID 또는 로컬 폴더 경로 |
| `quantization` | `4bit` | `4bit` / `8bit` / `none` |
| `max_gpu_memory` | `7GiB` | 넘치는 부분은 CPU RAM으로 offload |
| `output.timestamp` | `true` | `[00:03:21]` 시간 표시 |
| `audio.chunk_length` / `overlap` | `25` / `5` | 구간 길이와 겹침(초). 구간은 최대 30초 |
| `pdf.mode` | `auto` | `auto` / `text` / `images` / `off` |
| `diarization.enabled` | `true` | 화자 구분 보조 모델 사용 |
| `diarization.num_speakers` | `0` | 화자 수 (0 = 자동) |
| `diarization.threshold` | `0.7` | 자동일 때 같은 화자로 볼 기준. 화자가 너무 많이 나오면 올림 |

## 테스트용 옵션

`run.bat` 대신 명령 프롬프트에서 직접 실행할 수 있습니다.

```bat
.venv\Scripts\python.exe run.py --max-chunks 4
.venv\Scripts\python.exe run.py --no-pdf
.venv\Scripts\python.exe run.py --dry-run
.venv\Scripts\python.exe run.py 녹음.m4a 자료.pdf --no-open
```

- `--max-chunks 4`: 앞 4개 구간(약 1분)만 빠르게 확인
- `--no-pdf`: PDF 없이 오디오만 사용 (PDF 효과 비교용)
- `--dry-run`: 모델 없이 입력 파일, 구간 분할, 프롬프트만 확인
- 파일 경로를 직접 지정할 수도 있습니다.

## 문제 해결

- **모델을 불러오지 못했습니다**: Gemma 라이선스 동의와 `setup.bat`의 Hugging Face 로그인을 했는지 확인하세요. 다시 로그인하려면 `.venv\Scripts\hf.exe auth login`을 실행합니다.
- **CUDA out of memory**: 다른 GPU 프로그램(게임, 브라우저 하드웨어 가속 등)을 닫고 다시 실행하세요. 4bit 모드에서는 모델의 레이어별 임베딩(PLE, 수 GB)만 CPU RAM에 두고 나머지는 GPU에 올리므로 RAM은 16GB 이상을 권장합니다.
- **전사 결과가 엉뚱한 언어의 같은 말 반복**: 오디오가 모델에 제대로 전달되지 않는 경우입니다. `diagnose.bat`으로 확인하세요. (오디오 인코더가 4bit로 양자화되면 이렇게 됩니다. 현재 버전은 인코더를 원래 정밀도로 둡니다.)
- **CUDA 사용 가능: False**: NVIDIA 드라이버를 최신으로 업데이트한 뒤 `setup.bat`을 다시 실행하세요.
- 오류 상세 내용은 `output/logs/run_*.log`에 저장됩니다.

## 품질 확인: 기준 전사와 비교

Gemini 등으로 만든 기준 전사가 있으면 결과와 글자 단위로 비교할 수 있습니다 (화자 표기, 시간, 마크다운, `[웃음]` 같은 태그는 제외).

```bat
.venv\Scripts\python.exe tools\compare.py "output\녹음_transcript.txt" Gemini_answer.txt
```

- `precision`: 결과 중 기준에도 있는 글자 비율. `--max-chunks`로 앞부분만 돌렸을 때도 의미가 있습니다.
- `recall`: 기준 중 결과에도 있는 글자 비율. 녹음 전체를 돌렸을 때 의미가 있습니다.

## 실측 결과 (RTX 5060 8GB, 11분 연구실 미팅 + 발표자료 PDF, Gemini 결과 기준)

앞 6구간(약 2분) 기준:

| | E4B (4bit) | 12B Unified (QAT, 4bit) |
|---|---|---|
| Gemini와 일치 (precision) | **90.7%** | 38.0% |
| 25초 구간당 시간 | 약 10~16초 | 130~307초 |
| 최대 VRAM | 6.9GB | 9.4GB (8GB 초과 → 공유 메모리로 넘침) |
| 화자 구분 | 안 됨 | 안 됨 |

E4B로 11분 전체 (Gemini 기준):

| 방식 | 화자 턴 (Gemini 143) | precision | recall | 소요 | 최대 VRAM |
|---|---|---|---|---|---|
| Gemma만, 25초 구간 | 45 (대부분 Speaker 1) | 84.3% | 79.4% | 7분 31초 | 8.1GB |
| 화자 구분 보조 + 겹침 해소 | 119 | 80.8% | 74.4% | 약 9분 | 5.6GB |
| **+ 턴 병합(3초), 오디오 개수 명시, 빈 턴 재전사 (현재 기본값)** | 157 | 76.7% | 70.5% | 7분 6초 + 화자 구분 | 5.7GB |
| (참고) 글자가 적은 턴까지 재전사 | 165 | 74.4% | 75.3% | 10분 43초 | 5.7GB |

- 화자 구분을 넣으면 대화 구조(누가 언제 말했는지)는 Gemini와 거의 같아지지만, 턴을 잘게 나눠 넣는 만큼 글자 일치율은 몇 % 떨어집니다. 남은 오류의 대부분은 E4B 자체의 받아쓰기 오류(예: "엡실론" → "다음이형")라서 파이프라인 조정으로 더 줄이기 어렵습니다.
- 화자 구분(CPU) 시간은 같은 녹음에서도 78초~402초로 크게 달랐습니다. 원인은 확인하지 못했습니다.

- **E4B**: 발화 내용은 잘 받아쓰지만, 교수님과 학생의 대화를 한 사람의 발화로 묶습니다. 문장마다 화자를 물으면 1, 2, 1, 2로 기계적으로 번갈아 답합니다. thinking 모드로는 턴을 나누지만 두 명을 네 명으로 세고, 구간당 80~100초가 걸립니다.
- **12B**: 문장별 화자 판정은 E4B보다 나았지만(10개 중 8개 일치), 받아쓰기가 부정확하고("나누기 0" → "나노 20"), 앞 구간 내용을 다시 출력하거나 같은 말을 수백 번 반복했습니다. PDF 문맥이 붙으면 8GB를 넘어 매우 느려집니다.
- Gemini는 같은 녹음을 143개 턴으로 나눴습니다. **단일 로컬 모델로 Gemini 수준의 화자 구분은 현재 하드웨어에서 확인하지 못했습니다.**

## 12B 모델 비교 시 메모리 참고

- 작업 관리자의 "GPU 메모리"(예: 23.9GB)는 **전용 VRAM 8GB + 공유 GPU 메모리(시스템 RAM의 절반)** 를 더한 값입니다. 실제 VRAM은 8GB입니다.
- 모델이 전용 VRAM을 넘으면 Windows가 공유 GPU 메모리(시스템 RAM)로 넘겨 **오류 없이 크게 느려집니다**. 12B처럼 큰 모델을 쓸 때는 작업 관리자에서 "공유 GPU 메모리"가 늘어나는지 확인하세요.
- 녹음 하나가 끝날 때마다 로그에 `최대 VRAM 사용량`이 기록됩니다. E4B와 12B의 VRAM 사용량을 비교할 때 이 값을 쓰면 됩니다. 한계의 90%를 넘으면 경고가 함께 표시됩니다.
- 넘칠 때 느려지는 대신 바로 오류가 나게 하려면 NVIDIA 제어판 → 3D 설정 관리 → "CUDA - 시스템 메모리 폴백 정책"을 "시스템 메모리 폴백 선호 안 함"으로 바꾸세요.
- PLE가 없는 12B는 단어 임베딩과 출력층(약 2GB)을 자동으로 CPU RAM에 둡니다. 이것만으로 프롬프트 처리가 41초에서 1.6초로, 토큰 생성이 토큰당 0.9초에서 0.16초로 빨라졌습니다(PDF 없이 측정).
- E4B 기준 실측: 모델 로딩 후 4.1GB, PDF 포함 전사 중 최대 6.9GB, 25초 구간당 약 10~16초.
